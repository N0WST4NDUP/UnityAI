### A-1. Feudal HRL — "계급 지휘 체계" 강화학습

#### 무엇
- 커맨더 Agent와 유닛 Agent가 **역할은 계층적이지만 학습은 독립적**인 구조.
- 현실 군대 지휘 체계를 본뜸: 지휘관은 "목표"를 주고, 분대장은 "집행"한다.

#### 왜 중요한가
- 전에 논의했던 "커맨더 Policy가 유닛 Policy에 종속되면 안 된다"는 문제의 **해법**.
- 둘 다 RL인데 보상·학습 타이밍·관측을 완전히 분리해서, 한쪽이 다른 쪽의 습성에 맞춰 학습되는 걸 막음.

#### 기억해야 할 포인트
- **분리되는 것 3가지**: 보상 / 액션 공간 / 학습 타이밍(Stage)
- **연결되는 것 1가지**: 커맨더의 명령이 유닛의 관측으로 들어감 (이것만 인터페이스)
- 이 4가지 중 **연결되는 것이 늘어날수록 독립성은 약해진다**

#### 자가 점검
1. "독립 학습"이 왜 필요한지 한 문장으로 설명할 수 있는가?
2. 커맨더와 유닛을 잇는 유일한 통로는 무엇인가?
3. 만약 유닛에게 "팀 승리 시 +1.0 보너스"를 준다면 왜 안 되는가?

---

### A-2. 보상 독립성 원칙 — 유닛에 승/패 신호 금지

#### 무엇
- 유닛 Agent는 **명령 수행도 + micro 품질** 만으로 보상받음.
- 커맨더 Agent는 **승/패 + 팀 성과** 만으로 보상받음.
- 두 보상 사이에 공통 항목 **없음**.

#### 왜 중요한가
- 유닛이 "팀 이기면 +1" 이라는 신호를 받으면, 유닛은 "명령 따르기"보다 "이기기"를 학습함.
- 그러면 커맨더가 어떤 명령을 내려도 유닛은 자기 판단으로 승리에 유리한 행동을 함.
- 결과: 커맨더 명령의 영향력 약화 → 커맨더 학습이 유닛에 종속.

#### 기억해야 할 포인트
- 유닛 보상 = **수행도 80% + Micro 20%** (이 비율이 설계 기준)
- 사망 페널티는 작게 (`-0.1`). 크게 주면 유닛이 명령을 회피함 → 이것도 독립성 훼손.
- 시너지는 **유닛 보상 계수만** 조정. 커맨더 보상은 건드리지 않음.

#### 자가 점검
1. 유닛이 적을 처치했는데 명령 타겟이 아니었다면 보상은?
2. 유닛이 죽는 것에 큰 페널티를 주면 왜 문제인가?
3. 커맨더 보상에 "유닛이 명령을 잘 따랐는지"를 넣으면 왜 안 되는가?

---

### A-3. 명령(SquadCommand)이 왜 "관측"의 일부인가

#### 무엇
- 유닛 Agent가 받는 관측에 **자기 분대의 현재 명령 3필드**가 포함됨.
- 즉 명령은 `API 호출`이 아니라 `환경 상태`로 전달된다.

#### 왜 중요한가
- 명령을 함수 호출(`unit.SetTarget()`)로 주면 유닛이 수동적으로 반응만 함 → 학습 여지 없음.
- 명령을 관측으로 주면 유닛은 **"이 명령 하에서 어떻게 행동할지"** 를 학습함.
  - 예: "탱커 우선" 명령 + 주변 적 3명 관측 → 탱커가 누군지 판단 → 타겟 선택 학습.
- 이 설계 덕분에 **유닛이 명령을 "해석"하는 능력**이 생긴다.

#### 기억해야 할 포인트
- 명령 3필드:
  1. `target_position` — 어디로 갈지 (영역 좌표)
  2. `priority_filter` — 누굴 먼저 공격할지 (탱커/딜러/마법사/구조물/전체무시)
  3. `structure_handling` — 구조물 어떻게 할지 (부수기/우회/무시)
- **3필드 시작 → 학습 잘 안되면 자세·대형·퇴각조건 순으로 확장**
- 명령 갱신 주기 = **2초 고정 tick** (Phase 2 기준)

#### 자가 점검
1. "명령 = 관측"의 반대 설계(명령 = 함수 호출)는 왜 문제인가?
2. priority_filter 없이 target_position만 있으면 어떤 전략을 표현 못하는가?
3. 2초 tick은 빠른가 느린가? 매 프레임이면 뭐가 문제고, 10초마다면 뭐가 문제인가?

### A-4. 커리큘럼 학습 3단계

#### 무엇
학습은 한 번에 다 하지 않고 **단계별로**:

| Stage | 커맨더 | 유닛 | 학습하는 쪽 |
|---|---|---|---|
| 1 | 스크립트 (규칙) | 스크립트 (규칙) | 없음 (파이프라인 검증) |
| 2 | 스크립트 | **RL 학습** | 유닛 |
| 3 | **RL 학습** | ONNX Freeze (고정) | 커맨더 |

#### 왜 중요한가
- **Stage 1**: 유닛도 커맨더도 RL 없이 환경만 돌려봄 → 버그·파이프라인 문제 먼저 잡기.
- **Stage 2**: 커맨더를 규칙 기반으로 고정 → 유닛은 "정해진 명령들을 잘 수행하는 법" 만 배움.
- **Stage 3**: 유닛 정책을 **얼려놓고(freeze)** 커맨더만 학습 → 커맨더는 유닛에 종속되지 않는 고유 전략 학습.

#### 기억해야 할 포인트
- "Freeze"는 ONNX 파일로 뽑아서 추론만 돌린다는 뜻. 학습 중 가중치 업데이트 없음.
- Alternating (둘 다 RL, 교대로 freeze)은 **더 강해 보이지만 종속성 재등장** → 커리큘럼 후 선택지.
- Stage 2의 스크립트 커맨더는 **명령 어휘를 모두 써야** 한다. 유닛이 모든 명령 종류를 경험해야 Stage 3에서 커맨더가 그걸 활용 가능.

#### 자가 점검
1. Stage 2에서 유닛과 커맨더를 **동시에** RL로 학습하면 왜 문제인가?
2. Stage 3에서 유닛을 freeze 안 하면 무슨 일이 생기는가?
3. 스크립트 커맨더가 "탱커 우선 필터"를 한 번도 안 쓰면 Stage 3의 RL 커맨더에게 무슨 문제가 생기는가?

### B-1. ML-Agents 학습 루프 (Observe → Act → Reward)

#### 무엇
ML-Agents Agent의 매 스텝은 3단계:
1. `CollectObservations` — 현재 상태를 벡터로 수집
2. `OnActionReceived` — Policy가 낸 액션 받아서 실행
3. 보상 발행 (`AddReward` 또는 `SetReward`)

그리고 에피소드 종료 시 `EndEpisode`.

#### 왜 중요한가
- Phase 2의 모든 Agent 관련 TASK는 이 3단계 메서드를 구현하는 일.
- Observation / Action / Reward 중 **뭘 바꾸면 뭐가 영향받는지** 감을 잡아야 함.

#### 기억해야 할 포인트
- Observation 벡터 **크기가 바뀌면 ONNX 재학습** 필요. 신중하게 설계.
- Action: Continuous (연속 값, 이동 방향 등) vs Discrete (선택지, 타겟 선택 등). 섞어 쓸 수 있음.
- Reward는 스텝마다 작게 주거나, 에피소드 끝에 크게 주거나. 전자는 shaping, 후자는 sparse.

#### 자가 점검
1. Observation 벡터의 첫 인덱스가 "자기 HP"라고 하자. 학습 도중 여기에 "적 HP"를 추가하려면 무슨 일이 필요한가?
2. Sparse reward만 쓰면 왜 학습이 느린가?

### B-2. 관측 고정 크기 + 0 패딩

#### 무엇
- 유닛 수가 전투 중 변해도 Observation **벡터 크기는 고정**.
- 예: 분대 동료 최대 4명 슬롯 → 3명만 살아있으면 나머지 1슬롯은 0으로 채우고 `존재flag=0`.

#### 왜 중요한가
- Neural network 입력 크기는 고정이어야 함.
- 빈 슬롯을 그냥 0으로 두면 "이 슬롯이 없는 건지, 값이 0인 건지" 구분 못함 → `존재flag` 필요.

#### 기억해야 할 포인트
- 좌표·HP·거리 등은 **정규화** (0~1 또는 -1~1).
- 다른 유닛의 위치는 **자기 기준 상대 좌표**로 (회전·이동 일반화↑).
- 슬롯 정렬 기준 (예: 거리순) 이 학습에 영향을 줌.

#### 자가 점검
1. 정규화 안 하면 왜 문제인가?
2. 상대 좌표 대신 절대 좌표 주면 뭐가 불리한가?

---

### B-3. BehaviorName과 공유 Policy

#### 무엇
- ML-Agents는 같은 `BehaviorName`을 가진 여러 Agent가 **하나의 Policy를 공유**함.
- 우리 설계에선 `"UnitTank"`, `"UnitDealer"`, `"UnitMage"` 3개 BehaviorName → 직군별 공유.

#### 왜 중요한가
- 같은 직군 유닛들이 따로따로 학습하면 샘플 효율 나쁨.
- 공유 Policy면 한 직군의 모든 경험이 한 신경망에 쌓임.

#### 기억해야 할 포인트
- BehaviorName은 Inspector에서 설정 (BehaviorParameters 컴포넌트).
- Commander는 팀당 1명이라 별도 BehaviorName (`"Commander"`).
- ONNX도 BehaviorName 단위로 저장/로드.

#### 자가 점검
1. 모든 유닛이 같은 BehaviorName을 쓰면 무슨 문제가 생기는가?
2. 직군을 추가하면 BehaviorName은 몇 개 되는가?

### C-1. DI(의존성 주입) — FindGameObjectWithTag가 왜 나쁜가

#### 무엇
- 현재 `Unit.Awake`에서 `FindGameObjectWithTag("Manager")`로 매니저를 찾는다.
- TASK-210에서 이걸 생성자/Init 주입으로 바꿀 예정.

#### 왜 중요한가
- ML-Agents는 **학습 속도를 높이려고 여러 환경(Env)을 병렬 실행** 가능.
- 병렬 환경에선 씬에 "Manager" 태그 오브젝트가 여러 개 → Find가 엉뚱한 거 잡을 수 있음.
- Init 주입은 "어느 매니저를 쓸지" 명시적으로 지정 → 병렬 안전.

#### 자가 점검
1. 병렬 환경이 왜 학습에 유리한가?
2. Find 방식의 다른 단점 (테스트하기 어렵다 등) 떠올려보기.

---

### C-2. VectorSensor vs RaySensor vs GridSensor

- **VectorSensor**: 임의의 숫자 벡터. HP, 위치, 플래그 등.
- **RaySensor**: 부채꼴로 광선 쏴서 첫 충돌 거리·태그 반환. 주변 인지에 강함.
- **GridSensor**: 공간을 그리드로 나눠 각 셀의 상태를 채널로 표현. CNN 활용 가능.

우리 설계:
- 유닛 = VectorSensor + RaySensor
- 커맨더 = VectorSensor 시작, GridSensor 오버레이는 Phase 3 실험.

#### 무엇
